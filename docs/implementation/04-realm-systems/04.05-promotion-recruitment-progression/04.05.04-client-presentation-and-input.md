# Task 04.05.04: Present promotion progression in the client

Make available and locked promotion recruits understandable without changing existing input meanings.

## Status

- [x] Done

## Implementation notes

- The mandatory-choice HUD retains `[1] Queen`, `[2] Rook`, `[3] Bishop`, and `[4] Knight` at every tier. It renders all four as fixed buttons with textual `READY` or `LOCK >=threshold` states and distinct available/locked backgrounds, without relying on hue or unsupported UI glyphs.
- The interaction description identifies `BATCH SNAPSHOT`, shows the frozen total, the owned/governed/established `x2` breakdown, the next authored unlock and remaining points, and the shared reducer-enumerated available kinds. Live control changes cannot affect this canonical queued data.
- Keyboard and pointer selections converge on one submission path and are filtered through `legal_mandatory_choice_actions`. Locked selections produce the frozen score and required threshold as local feedback without changing state or creating a local/online action; reducer and server validation remain authoritative.
- Scenario-aware help documents the control formula, authored Bishop/Rook/Queen thresholds, stable bindings, and locked-input behavior. Local and online play share the same `DisplayedGame` projection, so reconnect snapshots drive the identical panel.
- The button row is bounded to the central bottom interaction region and temporarily owns the help-button layer while promotion is mandatory. Automated checks cover its fixed 22% side insets, height, authored thresholds, labels, and transactional locked input.
- Live X11 passes loaded a genuine two-choice promotion batch at both 800x480 and 1280x800. Text, buttons, board, and side panels remained disjoint; keyboard and pointer attempts on locked Queen displayed feedback while canonical revision stayed at 4. The same load exposed unrelated duplicate renderer despawn warnings, recorded separately as [Bug 018](../../bugs/018-duplicate-scenario-despawn.md).

## Scope

- Keep the established semantic bindings `[1] Queen`, `[2] Rook`, `[3] Bishop`, and `[4] Knight` in local and online play.
- Render every kind in the promotion panel, marking unavailable kinds as locked and showing each required score alongside the frozen current score.
- Show a compact score breakdown for owned, governed, and established settlement contributions plus the next unlock; clearly identify that this is the batch snapshot.
- Reject a locked local key or pointer choice before submission with clear feedback while retaining reducer/server validation as authority.
- Use the shared legal-choice representation for local play, online snapshots, help text, accessibility descriptions, and interaction previews.
- Fit the promotion content into the existing interaction/status region at supported window sizes without overlapping the board or side panels.

## Acceptance criteria

- Key meanings remain stable at every tier and Knight is always actionable.
- Available and locked choices are distinguishable through text or symbols without relying only on color.
- Every locked choice displays its threshold, and the panel displays the frozen score and next unlock.
- Changes to live board control while a batch is pending do not change the score displayed for that batch.
- Locked inputs show feedback and do not emit a valid action; forged or stale submissions are still rejected authoritatively.
- Keyboard, pointer, help, accessibility, local, and online paths describe the same available choices.
- Automated layout checks and a live-render pass cover narrow and standard windows without clipping or overlap.

## Cross-cutting concerns

- Stable input semantics, accessibility, client/server authority, bounded text, fixed screen ownership, responsive layout, and fog-safe presentation.
