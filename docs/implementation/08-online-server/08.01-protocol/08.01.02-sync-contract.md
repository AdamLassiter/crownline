# Task 08.01.02: Define synchronization contract

Require match ID, expected revision, and client-generated idempotency key on state-changing requests; return full authoritative snapshots after accepted actions.

## Status

- [x] Done

## Implementation notes

- Added a shared mutation context carrying match ID, expected revision, and client idempotency key to ready, action, draw, and rematch requests.
- Accepted mutation acknowledgements contain the exact cacheable result plus a full authoritative snapshot; the bounded per-match idempotency cache returns that original result without invoking a duplicate mutation closure.
- Authoritative snapshots carry match/revision, scenario ID/hash, canonical state/hash and clocks, and public room connection state, with validation against redundant canonical metadata.
- Stale revisions produce the stable `stale_revision` error code and current authoritative snapshot so clients can reconcile immediately.
- Join validation rejects incompatible protocol versions before room admission, and tests cover duplicate suppression, stale recovery, populated snapshot round-trip, and metadata drift.
- [Bug 006](../../bugs/006-piece-id-json-map-key.md) fixed the core `PieceId` JSON map-key deserializer exposed by populated authoritative snapshot tests.

## Acceptance criteria

- Duplicate keys return the original result without applying twice.
- Stale revisions return a current snapshot and stable error code.
- Snapshots include scenario identity/hash, canonical state, clocks, room state, and revision.
- Client and server protocol compatibility is checked before joining.

## Cross-cutting concerns

- Full snapshots are bounded for the maximum board and compressed only after measurement.
