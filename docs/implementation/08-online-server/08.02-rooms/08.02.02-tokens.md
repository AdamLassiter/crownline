# Task 08.02.02: Implement reconnect-token security

Issue a distinct high-entropy reconnect credential for each seat and authenticate all seat-scoped operations.

## Status

- [x] Done

## Implementation notes

- Each seat receives a distinct 244-bit UUID-v4-derived reconnect token only in its create/join response; room state retains only its SHA-256 digest.
- Ready, leave, and rematch operations hash the presented secret and compare fixed-size digests without data-dependent early exit before resolving a seat.
- The shared protocol wraps issued tokens in a serializer whose `Debug` representation is always `[REDACTED]`; stored digest debug output is redacted as well, and no token is accepted in a URL or included in errors/broadcast state.
- Missing rooms and wrong-seat tokens return the same unauthorized result. Failed attempts use a per-room-locator one-minute window and become rate-limited after eight failures.
- Tests cover token length/distinctness, raw-secret absence from stored/debug state, constant authenticated seat behavior, indistinguishable failures, and throttling.
- Room codes are shareable locators. Reconnect tokens are seat-specific secrets and must not be shared, logged, or placed in URLs.

## Acceptance criteria

- Raw tokens are returned only at issuance and stored hashed at rest.
- Constant-time verification is used where supported by the chosen hash primitive.
- Tokens never appear in normal logs, URLs, room broadcasts, or error bodies.
- Invalid token attempts are rate-limited and indistinguishable by seat existence.
