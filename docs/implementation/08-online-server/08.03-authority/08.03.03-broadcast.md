# Task 08.03.03: Broadcast snapshots and recover connections

Broadcast committed snapshots and room events to current seats and serve the latest state on authenticated reconnect.

## Status

- [x] Done

## Implementation notes

- Added the `/ws` endpoint with a bounded first-message authentication window. Reconnect credentials are carried in the validated authentication message, checked against the hashed room seat, and never placed in the URL.
- Connected clients subscribe to a latest-value snapshot channel and a bounded room-event ring. Slow consumers skip stale snapshots and recover from event lag using the current snapshot without blocking match actors.
- Match executors commit the prepared snapshot, journal record, clock/deadline, revision, outcome, and room lifecycle transaction before publishing. Persistence or socket-send failures cannot expose or roll back an uncommitted canonical action.
- Reconnect sends the latest revision, canonical state and clocks, draw offer, connection state, and rematch negotiation state. Terminal snapshots remain finished across disconnect notifications, and committed state synchronizes the in-memory room into rematch eligibility.
- Ready, action, draw, rematch, and leave messages are bound to the authenticated match and seat. Durable actor reload supports idempotent journal retries without attempting a second persistence transition.
- Tests cover latest-snapshot coalescing under 1,000 unpublished reads, commit-before-broadcast ordering, failed-persistence suppression, send-independent commits, terminal lifecycle persistence, disconnect behavior, and reconnect state completeness.

## Acceptance criteria

- Broadcast occurs only after persistence commits.
- Slow/disconnected clients cannot block match progress.
- Reconnect receives current revision, state, clocks, and outstanding draw/rematch state.
- Snapshot send failures do not roll back accepted actions.

## Cross-cutting concerns

- Bound per-connection outbound queues and favor latest snapshots over stale ones.
