# Task 08.04.01: Create SQLite schema and migrations

Define migrations for rooms, seats/token hashes, matches, canonical snapshots, revisions, clocks, outcomes, and append-only actions.

## Status

- [x] Done

## Implementation notes

- Added an explicit file/in-memory SQLite owner with foreign keys enabled, WAL journaling, five-second busy timeout, and selectable `FULL` or `NORMAL` synchronous durability.
- The initial forward-only transactional migration creates rooms, seats, matches, revisioned canonical snapshots, and append-only actions plus lifecycle/recovery indexes.
- Composite foreign keys require every current match revision and accepted action revision to have a matching snapshot. Primary/unique/check constraints cover room/seat identity, token-hash length, revisions, clocks, timestamps, outcomes, and idempotency keys.
- Snapshot/action blobs have hard byte limits; only fixed-size token hashes are represented in the schema, never raw reconnect tokens or unconstrained client blobs.
- Migration history is inserted in the same transaction, repeated startup applies each version once, and a database from a newer schema is rejected without mutation.
- Tests migrate a fresh temporary file, verify pragmas and single application, exercise foreign-key/uniqueness/revision constraints, and reject an injected future schema version.
