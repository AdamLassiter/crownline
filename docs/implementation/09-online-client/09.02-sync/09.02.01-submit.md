# Task 09.02.01: Submit revisioned idempotent commands

Translate UI actions into protocol requests with current revision and a unique key, then lock conflicting controls until resolution.

## Status

- [x] Done

## Implementation notes

- Extended the shared keyboard/pointer board interaction boundary with an online submission branch. Local matches still apply the reducer immediately; online matches enqueue an intent without mutating canonical state or playing a transition as final.
- The Bevy-side connection resource converts each accepted intent into one `ActionRequest` containing the authenticated match ID, the displayed canonical revision, and one UUID idempotency key. It retains that complete request while pending.
- Board selection and all conflicting move, Hold, promotion, and placement controls lock as soon as an online intent is accepted. The board help and persistent connection strip both expose the pending state and attempt count.
- A three-second response timeout resends a clone of the retained request through the bounded connection-worker channel. Reconnect and channel pressure preserve the original revision, action, and idempotency key rather than manufacturing a second intent.
- Matching acknowledgements unlock controls and then feed their authoritative snapshot through the existing validated adoption boundary. Acknowledgements for another key do not resolve the pending action.
- Retryable server failures retain the pending request for a same-key retry. Definitive, stale, wrong-seat/turn, and authoritative clock-expiry responses unlock controls; wrong-turn and clock-expiry paths immediately clear obsolete board selection.
- The WebSocket worker distinguishes an unauthenticated credential rejection from an authenticated wrong-seat command rejection, sends no raw server error copy to the UI, and carries actions/results through the existing bounded command and event queues.
- Tests prove online submission leaves canonical state untouched, a second control activation cannot replace the locked intent, repeated requests preserve revision and idempotency key, and wrong-turn/clock-expiry failures remain distinguishable.

## Acceptance criteria

- Retry reuses the same idempotency key for the same intent.
- Controls expose a pending state and prevent double-click duplication.
- Timeout of a request triggers sync/retry, not blind creation of a second intent.
- Wrong-turn and clock-expired errors immediately clear obsolete selection.
