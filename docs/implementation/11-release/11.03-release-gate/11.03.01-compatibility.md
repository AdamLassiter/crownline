# Task 11.03.01: Define compatibility and migration policy

Document version negotiation, supported save/scenario readers, database migrations, deprecation, and rollback behavior.

## Status

- [x] Done

## Implementation notes

- Added `docs/compatibility.md` with the conservative current support matrix: exact protocol/save/snapshot/journal/scenario version 1, local wrapper version 1, and forward SQLite database schemas 0/1/2 to current schema 2. Application version is explicitly provenance rather than a compatibility substitute.
- Defined independent version-increment triggers, source-version-selected migrations, permanent fixture/hash requirements for every newly supported reader, recoverable preservation of unsupported user data, deprecation expectations, and release-note/checklist obligations.
- Defined transactional forward-only database migration, mandatory verified pre-upgrade backup, rejection of newer schemas, same-schema rollback constraints, and backup restoration for rollback across schema increments; linked the policy to the operator runbook.
- Wired the existing `incompatible_protocol` error through HTTP create/join and WebSocket authentication/message handling. HTTP returns 426, both transports name the client and server protocol versions, and mismatches are non-retryable.
- Added a real loopback regression proving future-version clients cannot create or occupy a room seat, receive the typed actionable error, and leave the room available to a current-version join. Existing fixtures cover the only supported save/scenario source version and reject future versions; adding a supported legacy version now requires a permanent migration fixture by policy.

## Acceptance criteria

- Client/server mismatch fails before seat join with an actionable message.
- Database upgrades require a verified backup and are never auto-downgraded.
- Save/scenario migrations have fixture tests for every supported source version.
- Breaking compatibility increments the relevant independent version.

## Cross-cutting concerns

- Application version is not used as a substitute for schema/protocol versions.
